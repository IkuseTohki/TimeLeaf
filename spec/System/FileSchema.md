# データストレージ・ファイル設計仕様書

## 1. 概要

TimeLeafは、ネットワークが制限された環境下でのデータ同期を実現するため、フォルダベースのファイルストレージを採用している。
本仕様書では、DBを使用せずに不整合を解決し、チーム全体で最新状態を共有するための物理的なファイル構造と同期アルゴリズムを定義する。

設計の根幹は「不変（Immutable）な変更履歴の蓄積」であり、各ユーザーの操作（コミット）が独立したJSONファイルとして記録される。

## 2. 物理構造（フォルダ構成）

プロジェクトデータは、1つのルートディレクトリの下に、変更記録（JSON）が積み上がる形式で管理される。
各プロジェクトは、以下のディレクトリ構造を厳守しなければならない。

- **`{ProjectID}_{ProjectName}/`**: プロジェクトのルートディレクトリ。
- **`.project`**: プロジェクトの基本情報を保持する不変のメタデータファイル。
- **`users/`**: 全ユーザーのプロフィール情報を一元管理するフォルダ（プロジェクトと同階層）。
  - **`{GUID}.json`**: 表示名、テーマカラー等のプロフィールメタデータ。
  - **`{GUID}.png`**: アイコン画像の実体。
- **`changes/`**: すべての変更記録（JSON）を格納するフォルダ。
- **`snapshot.json`**: アーカイブ時に生成される、全履歴の集約済みファイル。
- **`history.zip`**: アーカイブ時に生成される、過去の変更履歴（JSON群）の圧縮ファイル。

## 3. ユーザープロフィール (.json)

`users/` フォルダ内に配置される、各ユーザーのアイデンティティを定義するファイル。

### 3.1. 保持する項目

| 項目            | 型       | 説明                                                          |
| :-------------- | :------- | :------------------------------------------------------------ |
| **Id**          | Guid     | ユーザーの一意な識別子。                                      |
| **DisplayName** | String   | 画面に表示されるユーザー名。                                  |
| **ThemeColor**  | String   | ユーザーを識別するための16進数カラーコード（例: `#2D5A27`）。 |
| **IconPath**    | String   | アイコン画像ファイルへの相対パス（例: `{GUID}.png`）。        |
| **UpdatedAt**   | DateTime | プロフィールが最後に更新された日時（JST）。                   |

## 4. プロジェクト・メタデータ (.project)

各プロジェクトフォルダの直下に配置され、プロジェクトのアイデンティティと作成時のコンテキストを保持する不変（Immutable）なファイルである。

### 3.1. 保持する項目

| 項目              | 型       | 説明                                                        |
| :---------------- | :------- | :---------------------------------------------------------- |
| **ProjectId**     | Guid     | プロジェクトの一意な識別子。                                |
| **CreatedAt**     | DateTime | 作成日時（ミリ秒 `fff` 精度を必須とする）。ソートの主キー。 |
| **CreatedBy**     | String   | プロジェクトを作成したユーザーの識別子。                    |
| **SchemaVersion** | int      | データの構造バージョン。                                    |

### 3.2. スキーマバージョンの運用ルール

将来的なデータ構造の変化に対応するため、以下のルールを適用する。

1. **前方互換性の担保**: アプリケーションは、自身のサポートするバージョン以下の `.project` を読み込むことができなければならない。
2. **上位バージョンへの対応**: アプリケーションが自身のサポート外（より新しい） `SchemaVersion` を検知した場合、データの破損を防ぐため、そのプロジェクトを「読み取り専用」として扱うか、ロードを中止して警告を表示しなければならない。
3. **マイグレーション**: スキーマ変更が必要な場合は、新しい `SchemaVersion` を定義し、アーカイブ（集約）処理等のタイミングでデータのアップグレードを行う。

## 4. ファイル命名規則

変更ファイル（コミット）の名称は、ソートによって適用の順序を確定できるよう、精密なタイムスタンプと一意の識別子を含める必要がある。

- **命名書式**: `{yyyyMMdd_HHmmss_fff}_{UserID}_{GUID}_{Category}.json`
- **タイムスタンプ (`yyyyMMdd_HHmmss_fff`)**: ミリ秒まで指定し、適用の時系列を決定する。
- **ユーザーID (`UserID`)**: 誰がその変更を行ったかを識別する。
- **一意の識別子 (`GUID`)**: 同一ミリ秒内に複数のファイルが生成された際の衝突を完全に回避する。
- **カテゴリ (`Category`)**: `EntityDefinition.md` で定義されたプロパティ・グループの種別。

## 5. カテゴリ別の保存・復元方式

データの性質に応じて、2つの異なる保存・復元アルゴリズムを使い分ける。

### 5.1. プロパティ・スナップショット（上書き型）

タスクの状態やスケジュールなど、一意の「現在の値」を持つデータに適用される。

- **単位**: 関連するプロパティ群（基本情報、進捗、スケジュール等）を1つのファイル（カテゴリ）にまとめる。
- **Task_Planning.json の構造**:
  - `TaskName` (String)
  - `Priority` (Enum)
  - `ScheduledStartDate` (DateTime)
  - `DueDate` (DateTime)
  - `EstimatedCost` (Double)
  - `AssigneeId` (Guid)
  - **`Constraints`** (Array): このタスクが依存する先行タスクのリスト。
    - `PredecessorId` (Guid): 先行タスクのID。
    - `Type` (String): 制約型（FS, SS, FF, SF）。
    - `LagDays` (Int): 猶予期間（日）。
    - `Description` (String): 制約の理由・メモ。
- **動作**: 変更が発生した際、そのカテゴリに属する**すべての最新の値**を新しいファイルとして書き出す。
- **保存の方向性**: データの整合性を保つため、常に「後続タスク（Successor）」のファイル内に「先行タスク（Predecessor）」への参照を保持する。
- **復元**: `changes/` 内のファイルを日時順に走査し、最新の値をメモリ上のエンティティに上書き（Replay）する。

### 5.2. インクリメンタル・レコード（蓄積型）

コメントや作業履歴など、過去の情報を失うことなく積み上げるデータに適用される。

- **動作**: 新しい投稿は、常に独立したユニークなIDを持つファイルとして生成される。
- **復元**: 特定のタスクに関連するすべてのファイルを読み込み、リストとして展開する。

## 6. 同期とコンフリクト解決（Replay アルゴリズム）

オフライン同期時に発生する可能性のある不整合を解決するため、以下のルールを適用する。

### 6.1. Last Writer Wins (LWW)

同一のプロパティ・カテゴリに対して複数の変更が存在する場合、**ファイル名に含まれるタイムスタンプがもっとも新しいもの**を「正」として採用する。
これにより、サーバーを介さずとも、各クライアントが独立して「最終的な状態」を決定できる。

### 6.2. データの再生手順

アプリケーション起動時、またはフォルダ更新検知時に以下の手順で状態を構築する。

1. **ファイル走査**: `changes/` フォルダ内の全JSONファイルをリストアップする。
2. **ソート**: ファイル名（タイムスタンプ）に基づいて昇順にソートする。
3. **適用（Replay）**:
   - **上書き型**: 対応するエンティティのプロパティを上書き。
   - **蓄積型**: 対応するリストに要素を追加。

## 7. アーカイブ・プロトコル

プロジェクトが長期化し、`changes/` 内のファイル数が増大した場合のパフォーマンス低下を防ぐための仕組み。

- **集約**: 全履歴をマージした `snapshot.json` を生成。
- **圧縮**: `changes/` フォルダを `history.zip` にまとめ、元の小ファイルを削除。
- **高速ロード**: アーカイブ済みの場合は `snapshot.json` 1つをロードすることで、Replay処理をスキップし起動を高速化する。
