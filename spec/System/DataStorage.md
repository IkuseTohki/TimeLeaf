# データストレージ・同期仕様書

## 1. 概要

TimeLeafは、ネットワークが遮断された環境下で、複数のユーザーがオフラインで作業を進めることを前提としたデータストレージ設計を採用している。
本仕様書では、DBを使用せず、フォルダ同期のみでデータの不整合を解決し、チーム全体で最新の状態を共有するための仕組みを定義する。

とくに、変更履歴を「カテゴリ（属性群）」ごとに分割して蓄積することで、コンフリクトを最小限に抑え、かつデータの消失を最小限に抑えることを目的としている。

## 2. 物理構造 (フォルダ・ファイル構成)

プロジェクトのデータは、1つのルートディレクトリの下に、変更記録（JSON）が積み上がる形式で管理される。
プロジェクト自身の情報は `changes/` 直下に、タスクごとの情報は ID 名のサブフォルダ内に配置することで、視認性と管理効率を両立する。

### 2.1. 階層構造

プロジェクトディレクトリは以下の構成を維持する。

- `{ProjectID}_{ProjectName}/`
  - `.project`: [Index] プロジェクトの存在証明（作成日時等のメタデータ）。
  - `changes/`: すべての変更記録を格納するフォルダ。
    - **プロジェクト情報の履歴** (直下に配置):
      - `yyyyMMdd_HHmmss_fff_{UserID}_Project_Basic.json`
      - `yyyyMMdd_HHmmss_fff_{UserID}_Project_Description.json`
      - `yyyyMMdd_HHmmss_fff_{UserID}_Project_Milestones.json`
      - `yyyyMMdd_HHmmss_fff_{UserID}_Project_Members.json`
    - **タスク情報の履歴** (サブフォルダ内に配置):
      - `{TaskID}/`
        - `yyyyMMdd_HHmmss_fff_{UserID}_Task_Progress.json`
        - `yyyyMMdd_HHmmss_fff_{UserID}_Task_Planning.json`
        - `yyyyMMdd_HHmmss_fff_{UserID}_Task_Description.json`
        - `yyyyMMdd_HHmmss_fff_{UserID}_Comment.json` (1件1ファイル)

### 2.2. ファイル命名規則

変更ファイルの名称には、ソートによって適用順序を確定できるよう、精密なタイムスタンプと属性カテゴリを含める。
**時刻情報はすべてJST（日本標準時）として扱う。**

- **タイムスタンプ**: `yyyyMMdd_HHmmss_fff` (JST、ミリ秒まで指定)
- **ユーザーID**: 誰がその変更を行ったか。
- **カテゴリ**: そのファイルが保持するデータの種類（`Project_Basic`, `Task_Progress` 等）。

## 3. 保存・同期方式

データの性質に合わせて、2つの異なる保存・復元アルゴリズムを組み合わせる。
**アプリケーション内部および永続化データにおけるすべての日時操作は、JST（日本標準時）に統一する。**

### 3.1. プロパティ・スナップショット（上書き型）

タスクの状態やスケジュールなど、一意の「現在の値」を持つデータに適用される。

- **単位**: 関連するプロパティ群（基本情報、進捗、スケジュール等）を1つのファイル（カテゴリ）にまとめる。
- **動作**: 変更があった際、そのカテゴリの最新の値を書き出す。**JSONデータ本体には更新日時を含めない。**
- ファイル名に含まれるタイムスタンプを、その変更が行われた時刻として扱う。
- **復元**: `changes/` 内のファイルを日時順に走査し、最新の値をメモリ上のエンティティに上書き（Replay）する。**最終的に読み込まれた最新ファイルのタイムスタンプを、エンティティの最終更新日とする。**

### 3.2. インクリメンタル・レコード（蓄積型）

コメントや作業履歴など、過去の情報を失うことなく積み上げるデータに適用される。

- **動作**: 新しい投稿は常に独立したファイルとして生成される。**JSONデータ本体には作成日時を含めない。**
- **時刻の真実性**: ファイル名に含まれるタイムスタンプを、そのレコードが作成された「唯一の真実の時刻」として扱う。
- **復元**: 同一IDに紐づくすべてのファイルを読み込み、リストとして展開する。**各レコードの `CreatedAt` は、それぞれのファイル名のタイムスタンプを元に復元する。**

### 3.3. プロジェクト・カテゴリ (カテゴリ分割)

データの性質とUIコンテキストに合わせて、以下のカテゴリに分割して保存する。

| カテゴリ名              | 含まれる主要プロパティ             | 更新頻度 |
| :---------------------- | :--------------------------------- | :------- |
| **Project_Basic**       | 名前、ステータス、健全性ステータス | 中       |
| **Project_Description** | 詳細説明                           | 低       |
| **Project_Milestones**  | マイルストーンのリスト全体         | 低       |
| **Project_Members**     | アサインされたユーザーIDのリスト   | 低       |

### 3.2. タスク・カテゴリ

| カテゴリ名           | 含まれる主要プロパティ                                         | 更新頻度 |
| :------------------- | :------------------------------------------------------------- | :------- |
| **Task_Progress**    | 進捗状態、実績開始/終了日、実績工数                            | **高**   |
| **Task_Planning**    | タスク名、優先度、開始予定日、期限、見積工数、担当者、依存関係 | 中       |
| **Task_Description** | 詳細説明                                                       | 低       |
| **Comment**          | (蓄積型：1投稿1ファイル) コメント本文、投稿者ID                | 中       |

## 4. コンフリクト解決ルール

オフライン同期時に、同一のデータに対して複数のユーザーが変更を行っていた場合に適用するルールである。

- **Last Writer Wins (LWW)**: 同一の `{EntityID}` かつ同一の `{Category}` に対する変更が複数存在する場合、ファイル名に含まれるタイムスタンプがもっとも新しいファイルを「正」として採用する。
- **GUIDの利用**: ID生成時にGUIDを使用することで、オフライン環境下で別々のユーザーが同じIDを生成することを完全に防ぐ。
- **カテゴリ間の独立性**: 例えば、Aさんが `Task_Progress` を更新し、Bさんが同時に `Task_Planning` を更新した場合、物理的に異なるファイルとして保存されるため、どちらの変更も失われることなくマージされる。

## 5. 実装上の考慮事項

- **Replay パフォーマンス**: `changes/` フォルダのファイル数が増大した場合の読み込み速度。
- **FileSystemWatcher**: 同期フォルダ内のファイル増分を検知し、アプリケーションの状態をリアルタイムに更新するための仕組み。

## 6. プロジェクトのアーカイブ

長期化したプロジェクトのパフォーマンスと整合性を維持するため、参照専用の状態へ移行する仕組みを提供する。

### 6.1. アーカイブ・プロトコル

不完全な同期によるデータの欠落を防ぐため、以下の手順でアーカイブを実行する。

1. **プロジェクト・ロック**: `.project.lock` ファイルを生成し、全ユーザーの書き込みをUIレベルで制限する。
2. **猶予期間**: ロック後、未同期ファイルが届くのを待つため、最終処理の実行を一定期間保留する。
3. **集約と圧縮**: 全履歴をマージした `snapshot.json` を生成し、`changes/` フォルダを `history.zip` に圧縮する。

### 6.2. 整合性の保護と参照

アーカイブされたプロジェクトは、高速なロードとデータの不変性を保証する。

- **高速ロード**: zipを解凍せず、集約済みの `snapshot.json` 1つをロードすることで瞬時に参照可能とする。
- **読み取り専用属性**: `snapshot.json` 等にOSレベルの「読み取り専用」属性を付与する。
- **改ざん検知**: `snapshot.json` のハッシュ値（SHA-256）を保持し、起動時に不整合を検知した場合は警告を発する。
