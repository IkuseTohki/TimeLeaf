# データストレージ・同期仕様書

## 1. 概要

TimeLeafは、ネットワークが遮断された環境下で、複数のユーザーがオフラインで作業を進めることを前提としたデータストレージ設計を採用している。
本仕様書では、DBを使用せず、フォルダ同期のみでデータの不整合を解決し、チーム全体で最新の状態を共有するための仕組みを定義する。

とくに、変更履歴を「蓄積（ログ）」することで、データの消失を最小限に抑え、かつ不整合の解決を予測可能に保つことを目的としている。

## 2. 物理構造 (フォルダ・ファイル構成)

プロジェクトのデータは、1つのルートディレクトリの下に、変更記録（JSON）が積み上がる形式で管理される。
これにより、特定のプロジェクト全体を「共有フォルダ」へコピーするだけで同期が可能となる。

### 2.1. 階層構造

プロジェクトディレクトリは以下の構成を維持する。

- `{ProjectID}_{ProjectName}/`
  - `.project`: プロジェクト全体の基本情報を保持するメタデータファイル。
  - `snapshot.json`: アーカイブ時に生成される、全履歴の集約済みファイル。
  - `history.zip`: アーカイブ時に生成される、過去の変更履歴（JSON群）の圧縮ファイル。
  - `changes/`: すべての変更記録を格納するフォルダ。
    - ファイル名: `yyyyMMdd_HHmmss_fff_{UserID}_{GUID}.json`

### 2.2. ファイル命名規則

変更ファイルの名称には、ソートによって適用順序を確定できるよう、精密なタイムスタンプと一意の識別子を含める。
**時刻情報はすべてUTC（協定世界時）として扱う。**

- **タイムスタンプ**: `yyyyMMdd_HHmmss_fff` (UTC、ミリ秒まで指定)
- **ユーザーID**: 誰がその変更を行ったか。
- **GUID**: 同一ミリ秒内に複数のファイルが生成された際の衝突回避。

## 3. 保存・同期方式

データの性質に合わせて、2つの異なる保存・復元アルゴリズムを組み合わせる。
**アプリケーション内部および永続化データにおけるすべての日時操作はUTCに統一する。** ローカル時刻への変換は、UIでの表示直前でのみ行う。

### 3.1. プロパティ・スナップショット（上書き型）

タスクの状態やスケジュールなど、一意の「現在の値」を持つデータに適用される。

- **単位**: 関連するプロパティ群（基本情報、進捗、スケジュール等）を1つのファイル（カテゴリ）にまとめる。
- **動作**: 変更があった際、そのカテゴリの最新の値を書き出す。**JSONデータ本体には更新日時を含めない。**
- ファイル名に含まれるタイムスタンプを、その変更が行われた時刻として扱う。
- **復元**: `changes/` 内のファイルを日時順に走査し、最新の値をメモリ上のエンティティに上書き（Replay）する。**最終的に読み込まれた最新ファイルのタイムスタンプを、エンティティの最終更新日とする。**

### 3.2. インクリメンタル・レコード（蓄積型）

コメントや作業履歴など、過去の情報を失うことなく積み上げるデータに適用される。

- **動作**: 新しい投稿は常に独立したファイルとして生成される。**JSONデータ本体には作成日時を含めない。**
- **時刻の真実性**: ファイル名に含まれるタイムスタンプを、そのレコードが作成された「唯一の真実の時刻」として扱う。
- **復元**: 同一IDに紐づくすべてのファイルを読み込み、リストとして展開する。**各レコードの `CreatedAt` は、それぞれのファイル名のタイムスタンプを元に復元する。**

## 4. コンフリクト解決ルール

オフライン同期時に、同一のデータに対して複数のユーザーが変更を行っていた場合に適用するルールである。

- **Last Writer Wins (LWW)**: 属性グループ（例：進捗グループ）への変更が複数存在する場合、ファイル名に含まれるタイムスタンプがもっとも新しいファイルを「正」として採用する。
- **GUIDの利用**: ID生成時にGUIDを使用することで、オフライン環境下で別々のユーザーが同じIDを生成することを完全に防ぐ。

## 5. 実装上の考慮事項

- **Replay パフォーマンス**: `changes/` フォルダのファイル数が増大した場合の読み込み速度。
- **FileSystemWatcher**: 同期フォルダ内のファイル増分を検知し、アプリケーションの状態をリアルタイムに更新するための仕組み。

## 6. プロジェクトのアーカイブ

長期化したプロジェクトのパフォーマンスと整合性を維持するため、参照専用の状態へ移行する仕組みを提供する。

### 6.1. アーカイブ・プロトコル

不完全な同期によるデータの欠落を防ぐため、以下の手順でアーカイブを実行する。

1. **プロジェクト・ロック**: `.project.lock` ファイルを生成し、全ユーザーの書き込みをUIレベルで制限する。
2. **猶予期間**: ロック後、未同期ファイルが届くのを待つため、最終処理の実行を一定期間保留する。
3. **集約と圧縮**: 全履歴をマージした `snapshot.json` を生成し、`changes/` フォルダを `history.zip` に圧縮する。

### 6.2. 整合性の保護と参照

アーカイブされたプロジェクトは、高速なロードとデータの不変性を保証する。

- **高速ロード**: zipを解凍せず、集約済みの `snapshot.json` 1つをロードすることで瞬時に参照可能とする。
- **読み取り専用属性**: `snapshot.json` 等にOSレベルの「読み取り専用」属性を付与する。
- **改ざん検知**: `snapshot.json` のハッシュ値（SHA-256）を保持し、起動時に不整合を検知した場合は警告を発する。
