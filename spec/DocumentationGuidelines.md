# ドキュメント記述ガイドライン (Documentation Guidelines)

本プロジェクト（TimeLeaf）におけるすべての仕様書、ADR、および設計ドキュメントは、人間とAI（LLM）の両方が文脈を正確に理解し、迷いなく実装へ落とし込める「AI-Native」なフォーマットにしたがって記述されなければならない。

## 1. 人間とAIに最適化された5つの原則 (Core Principles)

### 1-1. 関心の分離とファイル分割 (Modularity)

- **ルール:** 1つの巨大なファイルを作成してはならない。要件、アーキテクチャ、データモデル、UIなど、関心事ごとにディレクトリとMarkdownファイルを分割する。
- **理由:** 人間の認知負荷を下げるだけでなく、AIにコードを生成させる際、必要なファイルだけをコンテキストとして渡すことで「Lost in the Middle（中間情報の喪失）」を防ぎ、生成精度を最大化するため。

### 1-2. 「ユビキタス言語」の定義と英名併記 (Ubiquitous Language)

- **ルール:** プロジェクト特有の概念は `Glossary.md` に集約し、**必ず実装で用いる英名（変数名・クラス名）を併記**する。
- **理由:** 人間同士の認識ズレを防ぐとともに、AIがコード生成のたびに異なる変数名（ハルシネーション）を出力するのを完全に防ぐため。

### 1-3. 「やらないこと」の明記 (Non-Goals)

- **ルール:** 要件定義には、スコープ外（Out-of-Scope）の機能や制約を明記する。
- **理由:** プロジェクトの肥大化を防ぐとともに、AIが気を利かせて不要な機能（過剰なDB設定や認証ロジックなど）を勝手に実装してしまうのを防ぐため。

### 1-4. 曖昧な形容詞の排除と状態の厳密化 (Explicit I/O & State)

- **ルール:** 「使いやすい」「高速な」といった形容詞を避け、定量的な制約（Constraints）やデフォルト値、状態遷移を厳密に定義する。
- **理由:** AIには「空気を読んだ実装」ができないため、テスト可能な状態（State）として指示する必要がある。

### 1-5. 構造化フォーマットとテキスト図解 (Structured Format)

- **ルール:** 文書はMarkdownで構造化し、フローチャートやER図などの図解は画像ではなく Mermaid.js 等のテキストベース記述言語を使用する。
- **理由:** AIは画像内の意図を正確にパースできないため、テキストコードとして関係性を読み取らせる必要がある。

## 2. 脱AI構文とプロフェッショナルな記述ルール (Writing Style)

AIが生成しがちな「無機質で冗長な文章（AI構文）」を排除し、熟練のシニアエンジニアが書いたような、自然で説得力のあるドキュメントにするためのルールである。

### 2-1. 常体（だ・である調）と断定の徹底

- 「〜と考えられます」「〜する可能性があります」といった曖昧な推量表現を避け、「〜とする」「〜である」と簡潔かつ断定的に記述する。

### 2-2. 要求レベルの明確化 (RFC 2119準拠)

- 機能の優先順位や制約をAIに伝えるため、以下のキーワード（英語/日本語）を使用する。
  - **MUST (必須):** 絶対に満たさなければならない要件。
  - **SHOULD (推奨):** 強く推奨されるが、正当な理由があれば回避できる。
  - **MAY (任意):** オプションの機能。

### 2-3. 背景（Context）は文章で、要件（What/How）は箇条書きで

- 「なぜこれを作るのか（Why）」という背景や設計意図は、連続した自然な文章（パラグラフ）で記述する。
- 仕様の条件、制約、リストアップなどの構造的な部分のみ「箇条書き」を使用する。

### 2-4. 冗長な前置き・メタ発言の排除

- 「以下に〇〇の要件を示します」「これらが〇〇の仕様です」といった、進行に関するムダな修飾語を徹底的に削る。見出し（`#`）の直下から即座に本題に入る。

### 2-5. 設計の根拠と BDD フォーマットの活用

- 複雑な仕様には「なぜそのアプローチを採用したか（Design Rationale）」を添え、血の通ったドキュメントにする（必要に応じてADRを残す）。
- 複雑なロジックや振る舞いは、箇条書きの羅列ではなく `Given / When / Then` のBDD（振る舞い駆動開発）フォーマットを用いて具体例を記述する。

## 3. 仕様書の基本構成 (Standard Directory Structure)

本ガイドラインに従い、ドキュメントは以下の構造で管理・維持される。

```text
docs/
├── README.md                           # 目次・インデックス
├── DocumentationGuidelines.md          # 【本ドキュメント】記述ガイドライン
├── Glossary.md                         # 用語集（ユビキタス言語辞書）
│
├── 1_Requirements/                     # 要件定義（目的、スコープ、Non-Goals、ユースケース）
├── 2_Architecture/                     # システム設計（技術スタック、状態管理Hub）
├── 3_Schema/                           # データ設計（データモデル、ファイルストレージ・同期）
├── 4_UI/                               # UI/UX設計（レイアウト分離方針、画面要件）
├── 5_Testing/                          # テスト方針（Unit/Integration）
└── adr/                                # アーキテクチャ決定記録（背景とトレードオフの記録）
```
