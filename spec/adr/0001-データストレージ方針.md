# ADR-0001: オフライン環境下におけるフォルダベースのデータ同期方針

**ステータス (Status):** 承認済み (Accepted)
**作成日 (Created):** 2026-02-21

## 1. 背景 (Context)

本プロジェクトは、ネットワークが完全に遮断された、あるいは極めて制限された環境下でのチーム開発を支援することを目的としている。このような環境では、従来のクライアント・サーバー型データベース（RDBMS等）の導入やメンテナンス自体が大きな障壁となる。

また、物理的なメディア（USBメモリ等）や限られた帯域の共有フォルダを介して「ファイルを送り合う」ことで同期を実現する必要があり、以下の課題に対する堅牢なアプローチが求められた。

- データベース管理システム（SQL/NoSQL）をインストールせずに、どうやってデータを永続化するか。
- 複数のユーザーがオフラインで同時に作業した際、どのように変更を衝突させず、あるいは予測可能な形で統合するか。
- インポート/エクスポートといった煩雑な手順を排除し、フォルダの同期（OSレベルのファイル共有）だけで最新状態を維持するにはどうすればよいか。

## 2. 検討された代替案 (Considered Options)

### 案1: アクション・ベース (Action-based / Event Sourcing)

「タスク名を変更した」「状態を完了にした」といった、ユーザーの操作（イベント）の差分（Delta）をログとして記録する方式。

- **メリット:** コンフリクトの範囲を最小化でき、理論上はすべての履歴を正確に再現可能。
- **デメリット:** 実装の複雑性が極めて高い。過去の全イベントを正確にリプレイ（Replay）して現在の状態を組み立てるロジックの保守コストが大きい。

### 案2: エンティティ・スナップショット (Entity Snapshot)

変更のたびに「タスク全体の最新データ」を1つのJSONファイルとして書き出す方式。

- **メリット:** 実装が極めてシンプルであり、デバッグも容易。
- **デメリット:** 異なるプロパティ（例: 担当者と説明文）を別々のユーザーが同時期に編集した場合、一方の変更が丸ごと消失するリスク（上書きコンフリクト）が高い。

### 案3: プロパティ・スナップショット（採用案）

属性を関心事（基本情報、進捗、スケジュール等）でグループ化し、そのグループ単位でスナップショットを記録する方式。

## 3. 決定事項 (Decision)

属性の性質に合わせ、「プロパティ・スナップショット」と「インクリメンタル・レコード」を組み合わせたハイブリッド方式を採用する。

1. **属性データ（プロパティ・スナップショット）:** タスクの基本情報、進捗、スケジュールなどをカテゴリとしてグループ化し、グループ内のいずれかが変更されたら「グループ全体の最新値」を書き出す。
2. **蓄積型データ（インクリメンタル・レコード）:** コメントや作業ログなど、過去を消してはならないデータは、常に新しい独立したファイルとして生成する。
3. **コンフリクト解決ルール:** 同一カテゴリの競合時は、ファイル名のタイムスタンプに基づく **Last Writer Wins (LWW)** を採用する。
4. **識別子 (Identifier):** すべてのエンティティ（プロジェクト、タスク、メンバー、コメント等）のIDには `Guid` を使用し、オフライン環境でのID重複を完全に回避する。

## 4. 理由とトレードオフ (Rationale & Trade-offs)

本方式の採用は、**「実装のシンプルさ」と「オフライン環境でのデータ保護」のバランス**を最優先した結果である。

- **得られたメリット:** 異なる役割のユーザー（リーダーが計画を立て、開発者が進捗を打つ）であれば、更新するファイルが自然に分かれるため、実質的なコンフリクト発生率を低く抑えられる。
- **受け入れた代償（トレードオフ）:** 同一の属性カテゴリ（例: タスクの詳細説明）を二人が同時に編集した場合は、一方の変更が上書きによって失われる。これはオフライン環境という制約上、完全なマージは困難であると判断し、運用ルールやコメント機能での補完を前提とした。

## 5. 結果と影響範囲 (Consequences)

- 永続化層（Infrastructure）は、JSONファイルの走査とメモリ上でのマージ（Replay）を主軸とするため、`Repository` 層の実装およびI/Oパフォーマンスに大きく影響する。
- IDに連番（Auto Increment）が使えないため、UIでのソート順はIDではなく明示的な日時プロパティ（`CreatedAt` 等）に依存する必要がある。

## 6. 今後の展望・再評価のトリガー (Future Outlook & Re-evaluation Triggers)

- **ファイル数の限界:** `changes/` フォルダ内のファイル数が5,000件を超え、起動時のReplay処理に体感的な遅延（UIのフリーズ等）が生じた場合、アーカイブ・プロトコル（集約済み `snapshot.json` の導入）の実装をトリガーする。
- **不整合の頻発:** LWWルールによるデータの消失が、実運用においてユーザーの許容範囲を超えた場合、より粒度の細かいアクション・ベース（案1）への移行を再検討する。
