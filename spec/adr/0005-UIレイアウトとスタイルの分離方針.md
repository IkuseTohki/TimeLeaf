# UIレイアウトとスタイルの分離方針

## 背景

現在、TimeLeafのXAMLファイル（View）には、コントロールの配置（レイアウト）と見た目の装飾（スタイル）が混在している。
とくに `Margin`, `Padding`, `Width`, `Height`, `FontSize`, `Foreground` などのプロパティが各要素にインラインで直接記述されており、以下の問題が生じている。

1. **可読性の低下**: 構造を表すコードと装飾を表すコードが混ざり合い、画面の階層構造が把握しにくい。
2. **保守性の低下**: デザインの変更（例：余白の統一、フォントサイズの変更）を行う際、すべてのViewファイルを修正する必要がある。
3. **再利用性の欠如**: 同じような見た目のボタンやテキストでも、個別にプロパティを設定しているため、デザインの統一感を保つのが難しい。
4. **テーマ切り替えの困難さ**: 色やサイズがハードコーディングされている箇所があり、テーマ（Light/Dark/Forest）の切り替えに完全に対応できない。

## 決定事項

**XAMLにおける「レイアウト（配置）」と「スタイル（見た目）」を明確に分離する。**

View.xaml は UI の**構造と配置**のみを責務とし、**装飾やデザイン**に関する定義はすべて ResourceDictionary（`Styles.xaml` 等）に抽出する。

### 1. View.xaml に記述してよいもの（レイアウト）

- **コンテナ構造**: `Grid`, `StackPanel`, `DockPanel`, `Border` などの入れ子関係。
- **配置プロパティ**:
  - `Grid.Row`, `Grid.Column`, `Grid.RowSpan`, `Grid.ColumnSpan`
  - `Grid.RowDefinitions`, `Grid.ColumnDefinitions`
  - `DockPanel.Dock`
- **データバインディング**: `Binding`, `Command` などのロジックとの接続。
- **スタイル適用**: `Style="{StaticResource ...}"` などの参照。

### 2. ResourceDictionary に分離すべきもの（スタイル）

以下のプロパティは、原則として View.xaml に直書きせず、スタイルとして定義する。

- **サイズ・余白**: `Width`, `Height`, `Margin`, `Padding`
  - ※例外: `Grid` の `RowDefinition Height="*"`, `Auto` など、構造決定に不可欠なものは除く。
- **タイポグラフィ**: `FontSize`, `FontWeight`, `FontStyle`, `FontFamily`, `TextAlignment`
- **色彩・外観**: `Foreground`, `Background`, `BorderBrush`, `BorderThickness`, `CornerRadius`, `Opacity`, `Effect`
- **配置の微調整**: `HorizontalAlignment`, `VerticalAlignment`, `HorizontalContentAlignment`, `VerticalContentAlignment`
  - ※これらはコンテキストによって「配置」にも「見た目」にもなりうるが、共通コンポーネント（ボタン等）の内部配置はスタイル、コンテナ内での位置決めはレイアウトとする（迷う場合はスタイル推奨）。

### 3. 実装ルール

- **命名規則**: スタイル名は「役割 + コントロール名 + Style」とする（例: `SidebarLogoTextStyle`, `DialogHeaderStyle`）。
- **継承の活用**: `BasedOn` を活用し、`LeafKit.UI` の共通スタイルや、TimeLeaf 内の基底スタイルを継承して差分のみを定義する。
- **カプセル化**: 特定の View でしか使わないスタイルであっても、View の `<UserControl.Resources>` または専用の ResourceDictionary に分離し、メインの XAML ツリーを汚さない。

## メリット

- **Viewの簡素化**: XAMLのネストや属性が減り、UI構造が一目でわかるようになる。
- **デザインの一元管理**: 余白やフォントサイズを一箇所で変更できるようになり、デザイン修正やレビューが容易になる。
- **テーマ対応の強化**: すべての装飾がリソース経由になることで、動的なリソース切り替え（テーマ変更）が確実に行えるようになる。

## デメリット

- **ファイル数の増加**: スタイル定義ファイルが増える、または View ファイル内の Resources セクションが肥大化する。
- **初期コスト**: 既存の View をリファクタリングし、スタイルを抽出する作業コストがかかる。

## 備考

この方針は、既存コードのリファクタリングおよび新規開発において厳格に適用する。
とくに `LeafKit.UI` との役割分担（共通基盤 vs アプリ固有）も意識し、汎用的なスタイルは `LeafKit.UI` へのフィードバックも検討するが、まずは `TimeLeaf` 側での分離を優先する。

### リソース分割の方針（2026-04-29 追記）

`Styles.xaml` の肥大化を防ぎ、かつ全体最適化と共通利用を促進するため、以下の「ハイブリッド分割案」を採用する。

1. **機能・カテゴリ軸 (Functional Split)**: コントロールの種類や役割に基づいた分割。
   - `Typography.xaml`: フォントサイズ、ウェイト、カラー等。
   - `ControlStyles.xaml`: ボタン、テキストボックス等の基本部品スタイル。
   - `Layout.xaml`: 余白（Margin/Padding）、サイズ定数、影（Effect）等。
2. **ドメイン・コンテキスト軸 (Domain Context Split)**: 特定の主要機能領域で共通利用される高度なコンポーネントの分割。
   - `WorkspaceStyles.xaml`: ワークスペース関連（タスクカード、コンテナ、フロー図等）で横断的に利用するスタイル。

View 単位の分割は、共通利用を妨げるため原則禁止とする。新しいスタイルを作成する際は、まず上記のいずれかのカテゴリに該当しないか検討すること。
