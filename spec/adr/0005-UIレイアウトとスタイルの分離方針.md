# ADR-0005: UIレイアウトとスタイルの分離方針 (Separation of Layout and Style in XAML)

**ステータス (Status):** 承認済み (Accepted)
**作成日 (Created):** 2026-03-24

## 1. 背景 (Context)

現在、TimeLeafのXAMLファイル（`View`）には、コントロールの配置（レイアウト）と見た目の装飾（スタイル）が混在している。とくに `Margin`, `Padding`, `Width`, `Height`, `FontSize`, `Foreground` 等のプロパティが各要素にインラインで直接記述（ハードコーディング）されており、以下の深刻な問題が生じている。

1. **可読性の低下:** 構造を表すコードと装飾を表すコードが混ざり合い、画面の階層構造（Visual Tree）が把握しにくい。
2. **保守性の低下:** デザインの変更（例: 余白の統一、フォントサイズの変更）を行う際、すべてのViewファイルを探索・修正する必要がある。
3. **再利用性の欠如:** 同一の役割を持つUIコンポーネントであっても、個別にプロパティを設定しているため、アプリケーション全体でデザインの統一感を保つのが極めて困難である。
4. **テーマ切り替えの阻害:** 色やサイズがハードコーディングされているため、要件である動的なテーマ切り替え（Light / Dark / Forestテーマ）に完全に対応できない。

## 2. 決定事項 (Decision)

**XAMLにおける「レイアウト（配置・構造）」と「スタイル（装飾・見た目）」を完全に分離する（MUST）。**

`View.xaml` はUIの**構造、配置、およびデータバインディング**のみを責務とし、装飾やデザインに関する定義はすべて `ResourceDictionary`（`Styles.xaml` または `<UserControl.Resources>`）に抽出する。

### 2.1 View.xaml に記述を許可するもの（レイアウトと結合）

- **コンテナ構造:** `Grid`, `StackPanel`, `DockPanel`, `Border` 等の入れ子関係。
- **配置プロパティ:**
  - `Grid.Row`, `Grid.Column`, `Grid.RowSpan`, `Grid.ColumnSpan`
  - `Grid.RowDefinitions`, `Grid.ColumnDefinitions`
  - `DockPanel.Dock`
- **データバインディング:** `Binding`, `Command` 等のViewModelとの接続ロジック。
- **スタイル参照:** `Style="{StaticResource ...}"` および `DynamicResource` を用いたリソースへの参照。

### 2.2 ResourceDictionary に分離すべきもの（装飾とスタイル）

以下のプロパティは、原則として `View.xaml` 内のコントロールに直接記述（インライン定義）してはならない（MUST NOT）。すべて `<Style>` 定義として抽出すること。

- **サイズ・余白:** `Width`, `Height`, `Margin`, `Padding`
  - _(例外: `Grid` の `RowDefinition Height="Auto"` 等、構造決定に不可欠なものは許可する)_
- **タイポグラフィ:** `FontSize`, `FontWeight`, `FontStyle`, `FontFamily`, `TextAlignment`
- **色彩・外観:** `Foreground`, `Background`, `BorderBrush`, `BorderThickness`, `CornerRadius`, `Opacity`, `Effect`
- **配置の微調整:** `HorizontalAlignment`, `VerticalAlignment`, `HorizontalContentAlignment`, `VerticalContentAlignment`
  - _(注記: 共通コンポーネントの内部配置はスタイル、外側コンテナでの位置決めはレイアウトとするが、迷う場合はスタイルへの抽出を推奨する)_

## 3. 実装ルールとガイドライン (Implementation Rules & Guidelines)

### 3.1 命名規則と継承

- **命名規則:** スタイル名（`x:Key`）は「役割 + コントロール名 + Style」とする（MUST）。
  - _例: `SidebarLogoTextStyle`, `DialogHeaderStyle`_
- **継承の活用:** `BasedOn` プロパティを活用し、共通UIライブラリ（`LeafKit.UI`）の基底スタイルや、アプリケーション全体の基底スタイルを継承して差分のみを定義する（SHOULD）。

### 3.2 XAML実装のBefore/After (Example)

**【悪い例 (Before): レイアウトとスタイルが混在】**

```xml
<!-- View.xaml に装飾が直書きされており、テーマ変更に追従できない -->
<StackPanel Orientation="Horizontal" Margin="10,5,10,5">
    <TextBlock Text="{Binding UserName}"
               FontSize="16" FontWeight="Bold" Foreground="#333333"
               Margin="0,0,10,0" VerticalAlignment="Center" />
    <Button Command="{Binding EditCommand}"
            Content="Edit"
            Width="80" Height="30" Background="#007ACC" Foreground="White" />
</StackPanel>
```

**【良い例 (After): 構造と装飾の分離】**

```xml
<!-- View.xaml (構造とバインディングのみ) -->
<StackPanel Style="{StaticResource ProfilePanelStyle}">
    <TextBlock Text="{Binding UserName}" Style="{StaticResource ProfileNameTextStyle}" />
    <Button Command="{Binding EditCommand}" Content="Edit" Style="{StaticResource PrimaryActionButtonStyle}" />
</StackPanel>

<!-- Styles.xaml (装飾の定義) -->
<Style x:Key="ProfilePanelStyle" TargetType="StackPanel">
    <Setter Property="Orientation" Value="Horizontal" />
    <Setter Property="Margin" Value="10,5,10,5" />
</Style>
<Style x:Key="ProfileNameTextStyle" TargetType="TextBlock" BasedOn="{StaticResource LeafKit.BaseTextStyle}">
    <Setter Property="FontSize" Value="16" />
    <Setter Property="FontWeight" Value="Bold" />
    <Setter Property="Foreground" Value="{DynamicResource Theme.Colors.TextPrimary}" />
    <Setter Property="Margin" Value="0,0,10,0" />
    <Setter Property="VerticalAlignment" Value="Center" />
</Style>
```

## 4. 影響とトレードオフ (Consequences)

- **得られたメリット:**
  - **Viewの簡素化:** XAMLのネストや属性が劇的に減少し、UIの階層構造が一目で把握可能になる。
  - **デザインの一元管理:** 余白やフォントサイズを一箇所で変更可能になり、デザイン修正・コードレビューが容易になる。
  - **テーマ対応の強化:** すべての色や外観がリソース経由（`DynamicResource`等）になることで、テーマ変更（Light/Dark/Forest）が確実に動作する。
- **受け入れた代償（トレードオフ）:**
  - **ファイル構成の肥大化:** スタイル定義ファイルが増加し、定義と利用箇所が物理的に離れるため、小規模な変更でも複数ファイルを行き来する必要が生じる。初期の開発コスト・リファクタリングコストが増加する。

## 5. 備考 (Notes)

この方針は、既存コードのリファクタリングおよび新規開発において厳格に適用する。
とくに共通基盤 `LeafKit.UI` とアプリ固有UIの役割分担を意識し、汎用性の高いスタイルは `LeafKit.UI` へフィードバック（昇格）させるフローを構築する。当面は `TimeLeaf` 側での分離を最優先とする。

### リソース分割の方針（2026-04-29 追記）

`Styles.xaml` の肥大化を防ぎ、かつ全体最適化と共通利用を促進するため、以下の「ハイブリッド分割案」を採用する。

1. **機能・カテゴリ軸 (Functional Split)**: コントロールの種類や役割に基づいた分割。
   - `Typography.xaml`: フォントサイズ、ウェイト、カラー等。
   - `ControlStyles.xaml`: ボタン、テキストボックス等の基本部品スタイル。
   - `Layout.xaml`: 余白（Margin/Padding）、サイズ定数、影（Effect）等。
2. **ドメイン・コンテキスト軸 (Domain Context Split)**: 特定の主要機能領域で共通利用される高度なコンポーネントの分割。
   - `WorkspaceStyles.xaml`: ワークスペース関連（タスクカード、コンテナ、フロー図等）で横断的に利用するスタイル。

View 単位の分割は、共通利用を妨げるため原則禁止とする。新しいスタイルを作成する際は、まず上記のいずれかのカテゴリに該当しないか検討すること。
