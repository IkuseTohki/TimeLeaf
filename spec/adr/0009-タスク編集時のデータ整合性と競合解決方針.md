# ADR 0009: タスク編集時のデータ整合性と競合解決方針

## ステータス

承認済み

## 背景

現在、`TaskDetailViewModel` においてデータ保存はボタン押下時にのみ実行されるが、編集中のデータがメモリ上のモデルに直接反映されている。そのため、ユーザーが「キャンセル（破棄）」を選択してもメモリ状態が変更されたまま残るという整合性の欠如がある。また、他ユーザーによる外部変更が検知された際、現在の「即時自動再読み込み」仕様により、編集中データが強制的に書き換えられ、競合のリスクが生じている。

## 検討された案

1. **現行維持（対策なし）**
   - メリット: 変更不要。
   - デメリット: 破棄してもデータが戻らない。競合時に編集データが失われる。
2. **コピー・アプローチ（採用）**
   - 編集前にモデルのコピー（作業用データ）を作成し、破棄時はコピーを破棄、保存時のみマスターへマージする。
   - 外部変更検知は通知のみを行い、再読み込みはユーザーに委ねる。
3. **オプティミスティック・ロック案**
   - 最終更新時刻を監視し、保存時に競合を確認する。
   - メリット: 同期ロジックの変更が少ない。
   - デメリット: リアルタイムな状況把握（外部変更の即時可視化）が難しい。

## 決定

案2（コピー・アプローチ）を採用する。

1. **作業用モデルの保持**: `TaskDetailViewModel` 開設時に JSON シリアライザを用いてエンティティのディープコピーを作成し、UI はこれを使用する。
2. **外部変更検知の通知化**: 外部変更を検知した際は自動再読み込みをせず、UI 上に通知バナーを表示する。
3. **明示的な同期**: 通知バナー経由でのみ最新モデルの再読み込みを許可する。
4. **保存時の統合**: 保存ボタン押下時のみ、作業用データの内容をマスター（モデル）へマージし、保存処理を実行する。

## 理由・トレードオフ

作業用データを分離することで、破棄時のデータ復元が確実に行えるようになる。また、外部変更を「通知」に留めることで、現在の「即時同期」設計と競合せず、意図しないデータ上書きを防止できる。
トレードオフとして、コピー生成およびマージのロジックが必要となるが、これにより `IsDirty` 管理がより予測可能なものとなり、結果として UX の安定性が向上する。

## 結果・影響範囲

- `TaskDetailViewModel`: コピー生成/マージロジックの追加、イベント購読処理の変更。
- `ProjectTasksViewModel` / `MainViewModel`: 外部同期ロジック（自動リロード）を「通知」に限定するための変更。

## 今後の展望・再評価のトリガー

今後、プロジェクトの規模が拡大し、マージの競合頻度が許容できないレベルに達した場合、より複雑な差分マージ（3-way merge等）の実装を検討する。
