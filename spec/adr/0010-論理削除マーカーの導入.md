# ADR-0010: 論理削除マーカー (Tombstone Marker) の導入

**ステータス (Status):** 提案中 (Proposed)
**作成日 (Created):** 2026-05-02

## 1. 背景 (Context)
現在の論理削除実装はエンティティのプロパティ値に依存しており、Replay（起動時）処理においてすべての変更履歴ファイルをパースして状態を構築する必要がある。このため、タスク数や削除回数が増加すると、Replay 処理の I/O とメモリ消費が増大し、起動パフォーマンスを阻害する要因となっている。

## 2. 検討された代替案 (Considered Options)

### 案1: プロパティによる論理削除（現状）
- 内容: `IsDeleted` フラグ等をJSON内に保持。
- デメリット: 削除されたタスクもReplay時にパースが必要。

### 案2: 独立した削除マーカーファイル（Tombstone Marker）（採用）
- 内容: カテゴリ `Deleted` を持つファイル（Tombstone）を独立して作成する。

## 3. 決定事項 (Decision)
論理削除マーカー（Tombstone Marker）による削除管理を導入する（MUST）。

- **ファイルフォーマット:** `{yyyyMMdd_HHmmss_fff}_{UserId}_{GUID}_Deleted.json`
- **内容:** `{}` (空オブジェクト)
- **Replay 処理:** Repository 層は、ディレクトリ内のファイルリストアップ段階でこのカテゴリを検知した場合、**該当する GUID のタスクに関連するすべてのファイルをパース対象から即座に除外する**。これにより、Replay の計算コストを最小化する。

## 4. 理由・トレードオフ (Rationale & Trade-offs)
- **メリット:** 削除されたタスクのパースを完全にスキップできるため、起動時のパフォーマンスが劇的に向上する。
- **トレードオフ:** 論理的に「存在」しているタスクを削除済みと判定するための仕組みが、ファイルシステム上のファイル管理へと移るため、 Repository 層の読み込みロジックが複雑化する。

## 5. 結果と影響範囲 (Consequences)
- `Repository` 層の Replay ロジック（ファイル走査とデシリアライズ判定）を修正する必要がある。
- 既存の「プロパティによる削除」から、Tombstone 方式への移行マイグレーションが必要となる。

## 6. 今後の展望・再評価のトリガー (Future Outlook & Re-evaluation Triggers)
- 削除したタスクを完全に消去する「完全削除」機能の要望が上がった場合、Tombstone ファイルと関連する全履歴ファイルを物理的に削除するメンテナンス・プロセスの実装を検討する。
