# ADR (Architectural Decision Record) とは

ADRは、プロジェクトにおける**「重要な設計上の決定」と、その「背景・理由」を記録したもの**です。
長期にわたるソフトウェア開発プロジェクトにおいて、設計判断は当時の制約や目的に基づいて行われます。しかし、時間が経過すると「なぜこの構造を選んだのか」という文脈は失われがちです。ADRを記述する最大の目的は、将来の参画者や数カ月後の自分が、当時の意思決定プロセスを追体験し、納得感を持って開発を継続できるようにすることにあります。

## 1. 運用の目的と設計思想

ドキュメントの核となるのは、単なる決定事項の断片ではなく、意思決定に至る論理の保存です。以下の3つの観点を軸に運用します。

- **設計の透明性と納得感**: 「なぜそうなったか」を論理的に残すことで、後続の担当者が迷いなく実装やメンテナンスに取り組めるようにします。
- **知識の健全な継承**: 新しくプロジェクトに参加したメンバーが、現在の設計に至った「試行錯誤の歴史」や「妥当な妥協点」を素早く理解するための資産となります。
- **進化のための再考材料**: 環境の変化（技術トレンド、システム規模、要件の変遷）に合わせて、過去の決定を「不可侵のルール」にせず、当時の根拠に照らして再検討するための客観的な材料を提供します。

## 2. 記述のポイント

質の高いADRを作成するためには、箇条書きで結論を述べる前に、そこに至る思考の道筋を「地の文」で丁寧に解説することが重要です。とくに以下の要素を意識して記述してください。

### ① 意思決定という「選択」の記録

設計とは、常に複数の選択肢からのトレードオフの決断です。採用した案の妥当性を語るだけでなく、**「なぜ他の案を却下したか（不採用案のデメリット）」**を具体的に残してください。これが将来、当時却下した案を再検討すべきか判断する際の極めて重要な手がかりになります。

### ② 妥協（トレードオフ）の言語化

あらゆる要件を満たす完璧な設計は存在しません。何かを得るために何を犠牲にしたのかを明確にしてください。「実行速度を優先してメモリ効率を許容した」あるいは「将来の拡張性を捨てて、現在のデリバリー速度を優先した」といった**「意図的な妥協」**を記すことで、設計の境界線が明確になります。

### ③ 決定の有効期限と限界

その決定が有効であるための前提条件を記してください。「データ量が一定規模以内であればこの方式が最適である」といった**想定される限界**を記すことで、いつシステムを刷新・改善すべきかのトリガーを未来の自分たちへ予約できます。

## 3. ステータスの遷移（ライフサイクル）

設計判断は固定されたものではなく、実装の進展や環境の変化に応じて進化します。以下のステータスを用いて、その決定が現在どのようなライフサイクルにあるかを管理します。

- **提案中 (Proposed)**: 新しい設計案が提出され、レビューや議論を求めている段階。
- **承認済み (Accepted)**: チームで合意され、現在の設計・実装の公式な指針となっている状態。
- **実装完了 (Done)**: 設計に基づいたコードが実装され、意図通りに動作することが検証された状態。
- **要再評価 (Under Review)**: 当初の前提条件が変化し、現在の決定が妥当か再検証が必要な状態。
- **廃止 (Superseded)**: 新しいADRによって上書きされ、歴史的資料となった状態。

## 4. ファイル命名規則とテンプレート

ファイル名は、時系列順かつ検索性を高めるため `連番(4桁)-議題.md` (例: `0001-データストレージ方針.md`) とします。記述にあたっては、以下のテンプレートを基本としつつ、内容の複雑さに応じて地の文での解説を適宜追加してください。

```markdown
## ステータス

## 背景

（どのような課題や制約があったか。解決すべき問いや現状の懸念を叙述する）

## 検討された案

（どのような選択肢があったか。各案のメリット・デメリットを対比させる）

## 決定

（最終的に何を選んだか。具体的な構成、ルール、アーキテクチャを記述する）

## 理由・トレードオフ

（なぜそれを選んだか。何を優先し、何を妥当な代償として受け入れたかという論理）

## 結果・影響範囲

（この決定によって、他のどのモジュールや作業プロセスに影響が出るか）

## 今後の展望・再評価のトリガー

（将来的にどのような状況になったらこの決定を見直すべきか、あるいは次に検討すべき課題）
```
