# データストレージ・ファイル設計仕様書

## 1. 概要 (Overview)

TimeLeafは、ネットワークが制限された環境下でのデータ同期を実現するため、フォルダベースのファイルストレージを採用する。
本仕様書では、RDBMSを使用せずにデータの不整合を解決し、チーム全体で最新状態を共有するための物理的なファイル構造と同期アルゴリズムを定義する。

設計の根幹は「不変（Immutable）な変更履歴の蓄積」である。各ユーザーの操作（コミット）を独立したJSONファイルとして記録し、Event Sourcingの軽量版として振る舞うことで、オフライン環境特有のコンフリクトを安全に解決する。

## 2. 物理構造とファイル階層 (Physical Structure)

すべてのデータは、アプリケーションが指定する「全体データルートディレクトリ」配下に配置される。
各プロジェクトおよびシステムデータは、以下のディレクトリ構造を厳守する（MUST）。

```text
{TimeLeaf_Data_Root}/              # アプリケーション全体のデータ保存先
├── users/                         # 全ユーザーのプロフィール情報を一元管理するディレクトリ
│   ├── {UserId}.json              # プロフィール情報
│   └── {UserId}.png               # アイコン画像ファイル
└── {ProjectId}_{ProjectName}/     # 個別プロジェクトのルートディレクトリ
    ├── .project                   # プロジェクトの基本情報を保持する不変のメタデータ
    ├── changes/                   # すべての変更記録（JSON）を格納するディレクトリ
    │   ├── {yyyyMMdd_HHmmss_fff}_{UserId}_{GUID}_{Category}.json
    │   └── ...
    ├── snapshot.json              # [アーカイブ時のみ] 全履歴の集約済みファイル
    └── history.zip                # [アーカイブ時のみ] 過去の変更履歴の圧縮ファイル
```

## 3. ユーザープロフィール管理 (User Profiles)

`users/` ディレクトリ内で、各ユーザーのアイデンティティを定義・管理する。このデータはプロジェクトを横断して参照される。

### `{UserId}.json` のスキーマ定義

| プロパティ (`英名`)             | 型         | 説明                                                              |
| :------------------------------ | :--------- | :---------------------------------------------------------------- |
| **Id** (`Id`)                   | `Guid`     | ユーザーの一意な識別子（MUST）。                                  |
| **表示名** (`DisplayName`)      | `string`   | 画面に表示されるユーザー名（MUST）。                              |
| **テーマカラー** (`ThemeColor`) | `string`   | ユーザーを識別する16進数カラーコード（例: `#2D5A27`）（SHOULD）。 |
| **アイコンパス** (`IconPath`)   | `string`   | アイコン画像への相対パス（例: `{UserId}.png`）（MAY）。           |
| **更新日時** (`UpdatedAt`)      | `DateTime` | プロフィールが最後に更新されたJST日時（MUST）。                   |

## 4. プロジェクト・メタデータとスキーマ管理 (.project)

各プロジェクトルート直下に配置され、プロジェクトの存在証明と作成時のコンテキストを保持する不変（Immutable）なファイルである。生成後は変更してはならない（MUST）。

### `.project` のスキーマ定義

| プロパティ (`英名`)                      | 型         | 説明                                                           |
| :--------------------------------------- | :--------- | :------------------------------------------------------------- |
| **Id** (`ProjectId`)                     | `Guid`     | プロジェクトの一意な識別子（MUST）。                           |
| **作成日時** (`CreatedAt`)               | `DateTime` | JST日時。ミリ秒精度（`fff`）を必須とし、ソートの主キーとする。 |
| **作成者** (`CreatedBy`)                 | `string`   | プロジェクトを作成したユーザーの `UserId`。                    |
| **スキーマバージョン** (`SchemaVersion`) | `int`      | データの構造バージョン。初期値は `1`。                         |

### スキーマバージョンの運用ルール (Schema Versioning Rules)

オフライン特有のバージョン不一致によるデータ破損を防ぐため、以下のルールを適用する。

- **前方互換性の担保:** アプリケーションは、自身がサポートするバージョン「以下」の `.project` を必ず読み込めなければならない（MUST）。
- **上位バージョンの検知:** 自身がサポートするバージョンより新しい `SchemaVersion` を検知した場合、データの書き込みによる破損を防ぐため、プロジェクトを「読み取り専用」として扱うか、ロードを中止して警告を表示する（MUST）。
- **マイグレーション:** スキーマ変更時は、新しい `SchemaVersion` を定義し、アーカイブ（集約）等のタイミングでアップグレード処理を実行する。

## 5. 変更履歴ファイル命名規則 (Commit Naming Convention)

`changes/` に追加されるファイルの名称は、ファイルシステムのタイムスタンプに依存せず、文字列のソートのみで適用順序を確定できるよう厳密に定義する。

- **フォーマット (MUST):** `{yyyyMMdd_HHmmss_fff}_{UserId}_{GUID}_{Category}.json`
  - **Timestamp (`yyyyMMdd_HHmmss_fff`):** JST（日本標準時）。ミリ秒まで指定し、適用の時系列を決定する。
  - **UserId:** 変更を行ったユーザーのID。
  - **GUID:** 同一ミリ秒内に複数ファイルが生成された際の衝突を完全に回避するための一意の識別子。
  - **Category:** プロパティ・グループの種別（`Project_Basic`, `Task_Progress` 等）。

## 6. 保存・復元方式 (Persistence & Replay Strategy)

データの性質に応じ、2つの異なる保存・復元アルゴリズムを使い分ける。

### 6.1 プロパティ・スナップショット（上書き型）

タスクの状態やスケジュール等、単一の「現在の値」を持つデータに適用する。

- **単位:** 関連するプロパティ群を1つのカテゴリファイルにまとめる。
- **保存:** 変更時、そのカテゴリに属する**すべての最新の値**を新規ファイルとして書き出す。
- **復元:** ファイル名（昇順）で順次読み込み、エンティティのプロパティを上書き（Replay）する。

### 6.2 インクリメンタル・レコード（蓄積型）

コメント (`Comment`) 等、過去の情報を積み上げるデータに適用する。

- **保存:** 新しい投稿は、常に独立したユニークなIDを持つファイルとして生成する。
- **復元:** 関連するすべてのファイルを読み込み、リストの要素として展開する。

## 7. 同期とコンフリクト解決 (Replay Algorithm)

同一プロパティ・カテゴリに対して複数の変更が存在する場合、アプリケーション起動時およびフォルダ更新検知時に以下の手順で状態を構築する。

- **Last Writer Wins (LWW):** ファイル名に含まれるタイムスタンプがもっとも新しいものを「正」とする。これにより、サーバーを介さず各クライアントが自律的に最終状態を決定する。

### Replay実行の振る舞い (BDD)

- **Given:** `changes/` フォルダ内に複数のコミットファイルが存在する
- **When:** アプリケーションがデータ同期（Replay）を実行する
- **Then:** 以下のステップでインメモリの状態を構築する
  1. `changes/` 内の全 `.json` ファイルのパスをリストアップする。
  2. ファイル名（文字列）の昇順（A-Z）でリストをソートする。
  3. ソート順に従いファイルを読み込み、上書き型はプロパティを更新、蓄積型はリストへ追加する。

## 8. アーカイブ・プロトコル (Archiving Protocol)

プロジェクトが長期化し、`changes/` 内のファイル数増大によるパフォーマンス低下を防ぐ機能。

- **集約:** 全履歴のReplay結果をマージした `snapshot.json` を生成する。
- **圧縮:** `changes/` フォルダ全体を `history.zip` に圧縮し、元の小ファイルを削除する。
- **高速ロード:** `snapshot.json` が存在する場合はReplay処理をスキップし、該当ファイル1つをメモリにロードすることで起動を高速化する（MUST）。
